# Adversarial Review

## Purpose
Try to invalidate the concept before the user spends heavily on it.
Do not brainstorm features by default. Prefer subtraction, clarification, scope reduction, and testable assumptions.

# 1. Critical Assumptions
List 1–5 using:

```text
We believe ______ must be true for this game to work.
```

# 2. Riskiest Assumption
Choose one and classify it:

- Experience Risk
- Retention Risk
- Scope Risk
- Technical Risk
- Production Risk
- Market Risk
- Accessibility Risk
- Team Fit Risk

# 3. Blind Spots
Look for hidden production dependencies, accessibility constraints, device requirements, cognitive overload, novelty decay, replay fatigue, tutorial dependency, content explosion, narrative–mechanic conflict, and trailer communication problems.

# 4. Failure Modes
Ask:

> If this game fails, what is the most plausible reason?

# 5. Kill Criteria
Create observable criteria. Avoid vague “players do not like it” statements.

# 6. Pivot Paths
Specify:

**Preserve:**  
**Change:**  
**Why:**  

# 7. Anti-Feature Rule
When criticism appears, do not automatically add progression, inventory, skill trees, meta systems, crafting, extra modes, or narrative layers.

First ask:

> Can the problem be solved by making the nucleus clearer or smaller?

# 8. Versioning Rule
If refinement materially changes Player Promise, Design Nucleus, or Primary Core Loop, create a new Concept Version.
Do not hide a Pivot inside a score increase.
